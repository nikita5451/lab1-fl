# Інтерфейси: формат даних, контракт моделі, протокол

Усі багатобайтові поля мають порядок little-endian.

## 1. Формат файла локальних даних (data_N.bin, test.bin)

Заголовок 20 байтів, далі n записів по 65 байтів.

| Зсув | Розмір | Поле | Значення |
|-|-|-|-|
| 0 | 4 | магічне число | ASCII FLDS (u32 0x53444C46) |
| 4 | 2 | версія | 1 |
| 6 | 2 | кількість ознак | 64 |
| 8 | 2 | кількість класів | 10 |
| 10 | 2 | прапорці | біт 0: ознаки є uint8, ділити на 255 |
| 12 | 4 | n | кількість семплів |
| 16 | 4 | crc32 | CRC-32 (zlib) усіх байтів після заголовка |

Запис: 64 байти ознак (зображення 8×8 у градаціях сірого, по рядках, значення від 0 до 255) і 1 байт класу (від 0 до 9). Розмір файла дорівнює 20 + n·65 байтів. Для data_0.bin: 20 + 152·65 = 9900 байтів.

Нормалізація входу є частиною контракту: x = байт / 255.0, значення потрапляють у проміжок від 0 до 1. Пристрій і хост нормалізують однаково. Розбіжність не дає помилки, а лише знижує точність (FL-03). Значення набору UCI від 0 до 16 масштабовано у діапазон uint8 за формулою round(v/16·255).

Розміщення на пристрої: розділ флеш-пам'яті fldata (тип 0x40, підтип 0x01, зсув 0x110000, розмір 0x10000), який прошивається окремо від коду командою esptool write_flash 0x110000 data_0.bin. Прошивка при кожному старті перевіряє магічне число, версію і CRC, оскільки флеш-пам'ять може деградувати.

Поділ train і val (FL-04): індекси від 0 до n-1 перемішуються генератором fl_rng із seed 12345 (Fisher-Yates), далі n_val = n/5, n_train = n - n_val. Валідація це останні n_val перемішаних індексів, тренування решта, тому множини не перетинаються за побудовою. Для data_0.bin: 122 і 30.

## 2. Контракт моделі

Мережа: x[64] -> W1, b1 -> ReLU -> W2, b2 -> softmax[10], прихований шар 16 нейронів. Параметри передаються одним плоским масивом float32 little-endian, row-major.

| Блок | Форма | Елементів | Байтові зсуви |
|-|-|-|-|
| W1 | [16][64] | 1024 | 0 ... 4095 |
| b1 | [16] | 16 | 4096 ... 4159 |
| W2 | [10][16] | 160 | 4160 ... 4799 |
| b2 | [10] | 10 | 4800 ... 4839 |

Разом 1210 елементів, 4840 байтів: (n_in·n_hid + n_hid + n_hid·n_out + n_out)·4 = (64·16 + 16 + 16·10 + 10)·4.

Чому порядок і порядок байтів є контрактом: масив плоский і без імен, приймач не може перевірити, що лежить на кожному місці. Якщо хост і пристрій розійдуться (наприклад, W2 перед b1 або big-endian), нічого не впаде: числа потраплять не в ті ваги, і точність стане майже випадковою. Це неможливо відрізнити від складних даних, тому порядок фіксується цим документом і перевіряється CRC.

Детермінована ініціалізація від seed: s = fl_rng_seed(seed); усі біаси дорівнюють 0; W1[i] = (2u - 1)·sqrt(6/(64+16)); W2[i] = (2u - 1)·sqrt(6/(16+10)), де u це послідовні значення fl_rng_uniform(&s) у проміжку [0, 1): спершу всі W1 (по рядках), потім усі W2. Генератор xorshift32 (зсуви 13, 17, 5), u = (наступне >> 8) / 2^24.

Контрольні точки: CRC-32 упакованих ваг для seed 1 дорівнює f8692cac, для seed 7 дорівнює c40a1c43. Плата видає це число командою INIT 1 (потім CRC).

## 3. Транспорт

- Канал: нативний USB-serial ESP32-S3 (на хості /dev/ttyACM*), текстовий протокол, один рядок на команду.
- Максимальна довжина рядка 1100 байтів (рядок W займає 2 + 1024 символи). Довший рядок дає ERR line_too_long.
- Повідомлення прошивки йдуть тим самим каналом: хост пропускає незнайомі рядки і приймає лише відповідь OK, назва якої збігається з надісланою командою.
- Після перезавантаження плата друкує OK ready n=<N> і повторює рядок BOOT кожні 1.5 с, доки хост не надішле перший байт. Хост має вичитати застарілі рядки перед першою командою.
- Відкриття порту на хості виконується з DTR=RTS=True: явне dtr=False і rts=False перед open() дає комбінацію, яка скидає плату при кожному відкритті.

## 4. Протокол «сервер і пристрій»

Кожна відповідь починається з OK або ERR. Рядки EV це журнал подій пристрою (t у мілісекундах від старту), рядки W це шматки ваг у base64.

| Команда | Відповідь |
|-|-|
| INFO | OK INFO in=64 hidden=16 out=10 params=1210 bytes=4840 n=152 train=122 val=30 fw=lr1-0.1 |
| CRC | OK CRC crc=<hex> |
| INIT <seed> | OK INIT seed=<s> crc=<hex> |
| SETW <байти> <crc_hex> | OK SETW ready lines=7; далі 7 рядків W <base64>; OK SETW bytes=4840 crc=<hex> або ERR SETW crc got=<hex> want=<hex> |
| GETW | OK GETW bytes=4840 crc=<hex> lines=7; далі 7 рядків W <base64> |
| FIT <епохи> <lr> [batch=16] [seed=1] [clip=0] | OK FIT n=<n_train> loss=.. acc=.. val_loss=.. val_acc=.. ms=.. us=.. dw=.. |
| EVAL | OK EVAL split=val n=<n_val> loss=.. acc=.. ms=.. us=.. |
| STATS | OK STATS fits=.. setw=.. getw=.. evals=.. w_rx_bytes=.. w_tx_bytes=.. |
| RESETSTATS | OK RESETSTATS |
| RESET | OK RESET crc=<hex>: порядок train_idx, ваги seed 1 і лічильники повернуто до холодного старту |
| невідома команда | ERR unknown_command <рядок> |
| будь-яка команда протоколу без даних у флеш-пам'яті | ERR no_data |

Помилки команд: ERR SETW bad_args expected_bytes=4840, ERR SETW bad_chunk, ERR SETW aborted got=<n> of <m>, ERR FIT usage: FIT <epochs> <lr> [batch] [seed] [clip], ERR line_too_long.

Діагностика (нижній регістр, працює і без даних): help, info (OK info chip=.. rev=.. cores=.. idf=.. fw=.. id=..), heap (OK heap free=.. min_free=.. stack_free_min=.. stack_size=..), restart (OK restart).

Передача ваг: 4840 байтів -> 7 рядків W <base64>: шість по 768 байтів (1024 символи base64) і сьомий із 232 байтів. Цілісність: CRC-32 (zlib) усіх 4840 байтів перевіряється в обох напрямках (FL-05); пристрій копіює ваги у модель лише після збігу CRC і зберігає їх копію як «глобальні», від якої рахується норма оновлення dw.

Команди читання семплів у протоколі немає (FL-01): це протокольне вираження того, що дані не покидають вузол. Інструмент check_federation перевіряє це за транскриптом обміну.

Приклад журналу подій одного FIT (формат підтверджено виводом плати):

```
EV t=704787 op=fit_begin epochs=10 lr=0.3 batch=16 n=122
EV t=705096 op=fit_end fits=5 ms=303 loss=0.0645 acc=0.9918 dw=5.5311 clip=1.0000
EV t=714946 op=eval split=val n=30 acc=0.9667 ms=4
```

## 5. Обсяг обміну

Корисне навантаження: 4840 байтів в кожен бік за раунд на клієнта, тобто 9680 байтів за раунд. Реально по дроту ваги коштують дорожче: base64 дає 4*ceil(4840/3) = 6456 символів, плюс префікс W і кінець рядка у 7 рядках (+21), тобто 6477 байтів на одну передачу.
